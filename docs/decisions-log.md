# 初期実装の判断ログ

octa v1 の初期実装を通しで進めるにあたり、仕様が未確定・複数の選択肢がありえた箇所で下した**仮の決定**を、あとで議論・見直しできるように記録する。ここは「なぜその場でそう決めたか」を残す運用ログであり、確定した基盤設計の正典は `docs/adr/` に置く。

各エントリの `見直しトリガ` が満たされたら、その決定を再検討する。

---

## D0. 作業ブランチ: main で直接進める

- **決定**: 個別 issue ごとの worktree を切らず、`main` 上で初期実装を通しで進め、プリミティブ単位でコミットする。
- **背景/理由**: リポジトリは scaffold 2 コミットのみの初期段階で、守るべき既存資産がなく、今回の作業は v1 の基盤ほぼ全体を横断的に作るため、issue ごとの worktree 分割はかえって煩雑。
- **見直しトリガ**: 複数エージェントで並行着手する運用に移る／レビュー単位を PR に分けたくなったら、以降はプリミティブ単位で worktree・ブランチを切る。

## D1. ストレージエンジンは sqlx + SQLite を継続

- **決定**: 試作の sqlx + SQLite（コンパイル時クエリ検証・`.sqlx` オフラインキャッシュ）を作り直さず継続する。
- **背景/理由**: エンジンの結論（グローバル単一 SQLite ＋ `repo_id` スコープ列）は SQLite 前提で確定済み。`sqlx-cli`（`cargo sqlx prepare`）がこの環境で動くことを確認したので、スキーマを大幅拡張してもオフラインキャッシュを再生成でき、コンパイル時検証の資産を保てる。rusqlite への作り直しは検証を失う割に利得が薄い。
- **見直しトリガ**: `cargo sqlx prepare` の運用が破綻する／非同期ランタイム（tokio）の重さが問題になるなら rusqlite 等へ移行を再検討。
- 正典: `docs/adr/0001-storage-foundation.md`

## D2. スキーマは migration 0001 を書き直す（マイグレーションチェーンを積まない）

- **決定**: repo スコープ・per-repo 連番・状態フラグ・依存・lock を含む新スキーマを、`migrations/0001_init.sql` を丸ごと書き直す形で導入する。0002, 0003… の差分マイグレーションは積まない。
- **背景/理由**: 物理保存先が `.git/octa/octa.db` から XDG グローバルストアへ変わるため、旧 DB は引き継がず新規作成になる。保護すべき本番データが存在しないグリーンフィールドなので、差分マイグレーションよりクリーンな単一スキーマの方が読みやすい。
- **見直しトリガ**: 一度でも実データを持つ利用者が出た後は、以降 append-only の差分マイグレーションに切り替える。

## D3. repo identity のキーは canonical git-common-dir パス

- **決定**: 「どの repo か」の同定キーを、`git rev-parse --git-common-dir` を正規化した絶対パスにする。
- **背景/理由**: no-remote repo でも動く（remote URL 非依存）／worktree 群は同一 common-dir を共有するので単一 identity に自然に解決される。repo-root path は worktree ごとに異なり不可、remote URL は no-remote で不可・複数/変更されうる。
- **見直しトリガ**: repo をマシン間で移動・リネームして identity を保ちたい要件が出たら、identity の抽象化（別キー・移行コマンド）を検討。
- 正典: `docs/adr/0001-storage-foundation.md`

## D4. 並行制御は WAL + busy_timeout、原子性は単文/トランザクションで担保

- **決定**: SQLite を WAL モード・`busy_timeout` で開き、複数手順の変更はトランザクションに包む。per-repo 連番は「MAX(number)+1 を計算する単一 INSERT 文」で原子的に採番する。原子的 lock は `locked_by` 列への条件付き UPDATE（compare-and-set）で実装する。
- **背景/理由**: 個人ツール規模の並行度は WAL の範囲内。単一 SQL 文・条件付き UPDATE は SQLite が原子性を保証するため、二重採番・二重 lock 取得を機構として防げる。
- **見直しトリガ**: busy_timeout 内に収まらない競合が観測されたら、キュー化やアプリ側ロックを検討。
- 正典: `docs/adr/0001-storage-foundation.md`

## D5. Issue のデフォルト状態集合

- **決定**: repo 初回利用時に既定の状態集合 `open`（starting）／`in_progress`／`closed`（terminal）を seed する。ロックはせず、機構としては追加・フラグ変更が可能。
- **背景/理由**: PRD は「状態は starting/terminal フラグを持ち、集合は運用、デフォルトはロックしない」とする。最小で意味のある既定として open/in_progress/closed を置く。`close`→closed・`reopen`→open は試作の挙動を維持。
- **見直しトリガ**: 状態設定 UX（追加・編集・移行の見せ方）は設計送りの別テーマ。そこで既定集合ごと再検討しうる。

## D6. list のデフォルトは「非 terminal」

- **決定**: `issue list` の既定は terminal でない状態の issue を表示。`--state closed` は terminal、`--state all` は全件。特定状態名でのフィルタも受ける。
- **背景/理由**: starting/terminal フラグの意味（拾える/完了）に沿う。試作テスト（open 既定・closed・all）とも互換。
- **見直しトリガ**: 状態が増えて open/closed の二分では不足したら、状態名ベースのフィルタ表現へ寄せる。

## D7. CLI 表面の分割方針: 案A（各プリミティブの CLI はそのプリミティブに同梱）

- **決定**: 「CLI ＋ skill の表面」を独立実装にせず、各プリミティブ実装がそのプリミティブの CLI（`octa issue` / `octa pr` / `octa wiki` / `octa label`）を同梱する。横断スコープ（cwd→repo 既定＋ `--repo` / `--all-repos`）は共通のグローバルオプションとして持つ。エージェント向け skill 層は本コミット群では未実装とし、フォローアップに送る。
- **背景/理由**: 表面を一括で出すのは 1 PR に収まらず、各プリミティブ実装に依存する。案A なら各プリミティブが自己完結し、表面がプリミティブと歩調を合わせる。skill 層は CLI が固まってからの方が薄く書ける。
- **見直しトリガ**: skill 層を実装する段で、CLI の I/O 契約（JSON 出力の形）を skill 側の必要に合わせて調整しうる。

## D8. revia 統合機構: 仮に embed（reference-and-embed）

- **決定**: PR のレビュー統合機構を、仮に **(a) embed** に置く（octa がレビュースレッドをエンティティとして記録し、revia は任意の表面）。実装は本 v1 では行わず、PR は「エンティティ＋ブランチ参照＋状態/コメント」までに留める。
- **背景/理由**: PRD のリスク緩和レバー「reference-and-embed はランタイム呼び出しよりハード依存を減らす」に沿う。revia 自身が初期段階でスタック/スレッド機構未確定のため、実装は据え置き、決定のみ仮置き。
- **見直しトリガ**: revia のスタック/スレッド機構が固まったら embed vs call を確定し、レビュー記録の主も併せて決める。
- 正典: `docs/adr/0002-revia-integration.md`

## D9. Wiki ページの同定と相互リンク

- **決定**: Wiki ページは repo スコープ内で `slug`（一意）＋ `title` ＋ `body` を持つ。相互リンクは本文中の `[[slug]]` 記法で表現し、機構としては「そのページを指す被リンク一覧」を引けるようにする（リンクは保存時に本文からパースして `wiki_links` に展開）。
- **背景/理由**: octa の Wiki はリポジトリの実ファイルではなくエンティティ。zk / GitHub Wiki 同様に slug ＋ `[[ ]]` リンクが最小で自然。被リンク照会があると「相互リンク」の要件を機構として満たせる。
- **見直しトリガ**: リンク記法やアンカー（見出し単位リンク等）の要望が出たらパーサを拡張。

## D10. ラベルグループの排他は付与時に機構強制

- **決定**: ラベルは repo スコープ。ラベルグループは `single`（単一選択）／`multi`（複数選択）を持ち、`single` グループのラベルを issue に付けると同グループの既存ラベルを機構として自動的に置き換える（相互排他）。グループ無しのラベルは併存自由。
- **背景/理由**: CHO の受入基準「単一選択グループは相互排他・複数選択グループは併存が機構として強制される」を満たす最小実装。具体タクソノミー（Type/Repo 等の意味）は運用に委ね同梱しない。
- **見直しトリガ**: Project 側ラベル（将来スコープ）を足す段で、スコープ境界（issue ラベル vs project ラベル）を再設計。
