# ADR 0002: revia 統合機構（embed vs call）

- Status: Proposed（仮決定・revia 成熟後に確定）
- Date: 2026-07-22

## Context

octa の PR はエンティティ（git ブランチに紐づくディスカッション/レビューのスレッドと状態）を提供する。diff アンカーの、スレッド型、マルチ AI のレビュー**体験**は octa の外＝revia の領分、という方向は確定済み。octa はレビューを作り直さず revia と統合する。

未決なのは**統合機構**である。

- **(a) embed**: revia の設計を参考に octa へ組み込む。この場合 octa がレビューのスレッドを記録する。
- **(b) call**: ランタイムで revia を呼び出す。この場合 revia がレビュー体験/記録を持つ。

レビュー記録の主がどちらかは (a)/(b) の帰結であり、独立した軸ではない。

## 決定（仮）

**(a) embed（reference-and-embed）を仮に採用する。** octa がレビュースレッドをエンティティとして記録し、revia は任意の表面（サーフェス）として参照する。

ただし本 v1 ではレビュー機構そのものは**実装しない**。PR プリミティブのスコープは「エンティティ＋ブランチ参照＋状態/コメント」までとし、レビュー体験は revia に委ねる。本 ADR は統合の方向づけを仮置きするに留める。

## 理由

- リスク緩和: revia 自身が初期フェーズでスタック機構・スレッド機構が未確定。ランタイム呼び出し（call）は 2 つの動く的を実行時に結合させ、revia の停滞・非互換が octa の PR レビューを直接ブロックする。**reference-and-embed は octa 側にレビュー記録を持つため、revia へのハード依存を減らす**。
- 境界維持: octa ＝ PR エンティティと記録の層、revia ＝ レビューの表面。embed でも octa は「記録」までで、diff アンカーのレビュー体験は revia に委ねられる。

## 却下（現時点）

- **(b) call**: revia のスタック/スレッド機構が未確定な今、実行時ハード依存を確定させるのは早い。revia が停滞・乖離した場合に octa の PR レビューが仕様未定/ブロックになる。

## Status / 見直し

- **Proposed（仮）**。revia のスタック機構・スレッド機構が固まった時点で embed vs call を確定し、レビュー記録の主（どちらがスレッドを保持するか）も併せて決める。
- 本決定は octa v1 の PR プリミティブ実装をブロックしない（v1 はレビュー機構を含まないため）。
